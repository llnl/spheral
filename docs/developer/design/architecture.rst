#####################
Spheral Architecture
#####################

This page gives a high-level tour of how Spheral is put together: the major
abstractions, how they relate, and how a time step flows through the code.  It
is intended for developers who want to modify Spheral or add new physics, and
for users who want to understand what their Python scripts are driving.

.. note::

   This is an overview, not an API reference.  When in doubt, the headers in
   ``src/`` are authoritative; the most important ones are referenced below.

Layered Structure
=================

Spheral is a C++ library of physics components that is wrapped for Python and
driven from Python scripts.

.. code-block:: text

   User Python script        problem setup, materials, run loop
          │
   SimulationControl/*.py    SpheralController, Spheral{1d,2d,3d,RZ}.py, restart/viz dumps
          │
   PYB11 bindings            src/PYB11 — pybind11 code generated by PYB11Generator
          │
   C++ core (src/*)          templated on Dimension: Dim<1>, Dim<2>, Dim<3>
          │
   Third-party libraries     MPI, RAJA/CHAI/Umpire, Eigen, Boost, Silo/HDF5, Polytope, ...

Almost all numerical work happens in C++.  Python is responsible for
constructing objects, wiring them together, and running the outer time loop,
and it can also be used to implement new physics (see
:ref:`Writing a Physics Package in Python`).

Dimension Templating
====================

Nearly every C++ class is templated on a ``Dimension`` traits type defined in
``src/Geometry/Dimension.hh``.  ``Dim<n>`` supplies the types appropriate for
``n`` spatial dimensions:

- ``Scalar``, ``Vector``, ``Tensor``, ``SymTensor``, and higher-rank tensors
  (``ThirdRankTensor``, ``FourthRankTensor``, ``FifthRankTensor``).
- Geometric types: ``Box`` / ``FacetedVolume`` (``Box1d``, ``GeomPolygon``,
  ``GeomPolyhedron``) and ``Facet``.
- ``nDim``, the number of dimensions.

Physics is therefore written once and compiled separately for each enabled
dimension (controlled by ``SPHERAL_ENABLE_1D/2D/3D``).  Explicit
instantiations are generated from small Python templates named
``*Inst.cc.py`` that live beside the source.  For example,
``src/SPH/SPHInst.cc.py`` expands to:

.. code-block:: c++

   #include "SPH/SPH.cc"
   namespace Spheral {
     template class SPH<Dim<2>>;   // one per enabled dimension
   }

Cylindrical (RZ) and spherical geometries are not separate dimensions; they are
implemented as specialized physics classes (e.g. ``SPHRZ``, ``SphericalSPH``)
built on the 2D and 1D instantiations.

Data Model
==========

NodeLists
---------

A **NodeList** (``src/NodeList``) is a collection of particles ("nodes"),
typically one per material.  It owns the fundamental per-node fields: position,
velocity, mass, and the smoothing tensor ``H``.  The class hierarchy is:

- ``NodeList`` — basic kinematic state.
- ``FluidNodeList`` — adds mass density, specific thermal energy, and an
  equation of state.
- ``SolidNodeList`` — adds deviatoric stress, plastic strain, damage, and a
  strength model.
- ``DEMNodeList`` — a separate branch for discrete element (granular) modeling.

Nodes in a NodeList are divided into **internal** nodes, which this process
owns and evolves, followed by **ghost** nodes, which are copies created by
boundary conditions or by neighboring MPI domains (see
:ref:`Boundaries, Ghost Nodes, and Parallelism`).

Fields and FieldLists
---------------------

A ``Field<Dimension, DataType>`` (``src/Field``) stores one value of
``DataType`` per node of a single NodeList.  A ``FieldList`` aggregates the
corresponding Fields across many NodeLists, and is the type most physics code
operates on: a loop over a FieldList visits every NodeList, then every node in
it.

Views
-----

For GPU execution, Fields, FieldLists, and NodeLists each have a lightweight
**view** counterpart (``FieldView``, ``FieldListView``, ``NodeListView``).
Views are trivially copyable handles that can be captured into RAJA kernels;
memory movement between host and device is handled through CHAI, and
``ViewManager`` helps organize view objects and their host/device
synchronization.  Classes that have both forms follow a value/view pattern in
which the value class owns the data and inherits from (or produces) the view
class.  See :doc:`../dev/gpu_dev` for lessons learned during the GPU port.

DataBase
--------

The ``DataBase`` (``src/DataBase/DataBase.hh``) is the registry of all
NodeLists in a problem.  It provides FieldLists spanning all (or all fluid, all
solid, ...) NodeLists, owns the ``ConnectivityMap``, and is the object that
physics packages and integrators query for global state.

State, Derivatives, and Update Policies
=======================================

The time-evolving data of a simulation lives in a ``State`` object
(``src/DataBase/State.hh``), a map from string keys to Fields, FieldLists, and
other objects.  Time derivatives live in a parallel ``StateDerivatives``
object.  Physics packages populate both during setup via
``registerState`` and ``registerDerivatives``.

Each item enrolled in ``State`` may carry an **update policy**, a subclass of
``UpdatePolicyBase`` that defines how that item is advanced:

- Generic policies (``src/DataBase``): ``IncrementState`` (``x += dt * dx/dt``,
  reading the derivative stored under the ``"delta "`` prefix),
  ``ReplaceState``, ``PureReplaceState``, ``MaxReplaceState``, and bounded
  variants.
- Physics-specific policies, e.g. in ``src/Hydro``: ``PressurePolicy``,
  ``SoundSpeedPolicy``,
  ``CompatibleDifferenceSpecificThermalEnergyPolicy``.

Policies may declare **dependencies** on other state keys.  ``State::update``
resolves these, applying each policy only after the policies it depends on
have run (so, for example, pressure is recomputed after density and energy are
updated).

This design decouples integrators from physics: an integrator never needs to
know what a field means.  It simply calls ``state.update(derivs, dt, t, dt)``
and the policies do the rest.

Physics Packages
================

Every physics model implements the abstract ``Physics<Dimension>`` interface
(``src/Physics/Physics.hh``).  The required methods are:

=============================== ==============================================
Method                          Purpose
=============================== ==============================================
``registerState``               Enroll fields and their update policies in ``State``
``registerDerivatives``         Enroll derivative fields in ``StateDerivatives``
``evaluateDerivatives``         Compute time derivatives (the core physics)
``dt``                          Vote on the time step; returns ``(dt, reason)``
``label``                       Name of the package
=============================== ==============================================

Optional hooks give packages control over the life cycle:

=============================================== ==============================
Method                                          When it is called
=============================================== ==============================
``initializeProblemStartup``                    Once, before the first step
``initializeProblemStartupDependencies``        Once, after all packages are set up
``preStepInitialize``                           Start of each step
``initialize``                                  Before each derivative evaluation
``finalizeDerivatives``                         After all packages evaluate derivatives
``postStateUpdate``                             After each ``State`` update
``finalize``                                    End of each step
``applyGhostBoundaries``                        When ghost node values are updated
``enforceBoundaries``                           When boundary conditions are enforced on internal nodes
=============================================== ==============================

Packages also declare what precomputed information they need, and the
integrator computes the union of all requests before each evaluation:

- ``requireConnectivity()`` — ``{conn, ghost, overlap, intersection}``
- ``requireVolumes()`` — ``{explicit, implicit, voronoi}``
- ``requireReproducingKernels()`` — ``{explicit, implicit, hessian}``

Packages may own their own boundary conditions (``appendBoundary``) and
sub-packages (``appendSubPackage``); a hydro package, for example, typically
brings along its smoothing-scale and artificial viscosity machinery.

Package Families
----------------

- **Hydrodynamics** (via ``GenericHydro``): ``SPH`` (SPH, ASPH, PSPH, RZ and
  spherical variants), ``CRKSPH``, ``FSISPH``, ``GSPH``, ``SVPH``, ``FVCRKH``.
  Most have ``Solid*`` variants that include material strength.
- **Hydro modifiers**: ``ArtificialViscosity``, ``ArtificialConduction``.
- **Material response**: ``Strength``, ``Damage``, ``Porosity``.
- **Geometry/kinematics support**: ``SmoothingScale`` (evolution of ``H``),
  ``RK`` (reproducing-kernel corrections), ``VoronoiCells`` (volumes).
- **Forces**: ``Gravity`` (oct-tree N-body), ``SPHGravity``,
  ``ExternalForce`` (via ``GenericBodyForce``), and ``DEM``.

Materials (``src/Material``, ``src/SolidMaterial``, ``src/LEOS``) are not
physics packages; they are attached to NodeLists and consulted by the
packages and update policies.

Integrators and the Time Step
=============================

An ``Integrator<Dimension>`` (``src/Integrator``) holds the ``DataBase``, the
list of physics packages, and the boundary conditions, and advances the
system one step at a time.  Available schemes include ``ForwardEuler``,
``PredictorCorrector``, ``SynchronousRK2``, ``CheapSynchronousRK2``,
``SynchronousRK4``, ``Verlet``, and the implicit ``BackwardEuler`` and
``CrankNicolson`` (via ``ImplicitIntegrator``).

``Integrator::step`` performs the common setup and then calls the derived
class's scheme:

#. Collect connectivity requirements from all packages.
#. Rebuild ghost nodes and the ``ConnectivityMap`` (``setGhostNodes``).
#. Construct ``State`` and ``StateDerivatives`` from the registered packages.
#. Apply ghost boundaries.
#. Run the scheme-specific step, retrying with a smaller time step if it fails.

A scheme-specific step, for example ``SynchronousRK2``, looks like:

.. code-block:: text

   preStepInitialize
   dt = selectDt(...)                          # minimum over all packages' dt votes
   initializeDerivatives → evaluateDerivatives → finalizeDerivatives
   state.update(derivs, dt/2)                  # update policies, in dependency order
   applyGhostBoundaries; finalizeGhostBoundaries
   initializeDerivatives → evaluateDerivatives → finalizeDerivatives   (midpoint)
   state.update(derivs, dt)
   applyGhostBoundaries; finalizeGhostBoundaries
   postStepFinalize                            # calls each package's finalize
   enforceBoundaries

Each ``*Derivatives`` call in this sequence simply loops over the physics
packages in the order they were appended.

Neighbors and Connectivity
==========================

Each NodeList owns a ``Neighbor`` object (``src/Neighbor``) —
``NestedGridNeighbor`` or ``TreeNeighbor`` — that finds candidate neighbors
within the kernel extent.  The ``DataBase``'s ``ConnectivityMap`` combines
these into a flat ``NodePairList`` of interacting pairs, including pairs that
cross NodeLists.

Physics loops are generally written over the ``NodePairList``, which maps well
to threaded and GPU execution.  Per-node neighbor lists are derived lazily
from the pair list when requested.  ``PairwiseField`` stores per-pair data,
for instance the pairwise accelerations used by the compatible-energy
discretization.

Kernels
=======

Interpolation kernels live in ``src/Kernel`` (B-splines, Wendland, Gaussian,
sinc, and others).  In practice a kernel is wrapped in a ``TableKernel``,
which tabulates the kernel and its derivatives for fast lookup; the
``TableKernel`` is what hydro packages and the controller take as an argument.
``src/KernelIntegrator`` provides integrals of kernel functions.

Boundaries, Ghost Nodes, and Parallelism
========================================

Boundary conditions subclass ``Boundary<Dimension>`` (``src/Boundary``):
``ReflectingBoundary``, ``PeriodicBoundary``, ``ConstantVelocityBoundary``,
``InflowOutflowBoundary``, ``AxisBoundaryRZ``, ``FacetedVolumeBoundary``, and
others.  Boundaries work primarily by creating ghost nodes, keeping their
values up to date (``applyGhostBoundary``), and correcting internal nodes that
violate the boundary (``enforceBoundary``).

**MPI domain decomposition is implemented as a boundary condition.**
``DistributedBoundary`` and its subclasses (``TreeDistributedBoundary``,
``NestedGridDistributedBoundary``, ``BoundingVolumeDistributedBoundary``) in
``src/Distributed`` create ghost nodes for particles owned by neighboring
processes and exchange their values.  As a result, physics packages are
largely unaware of parallelism: they see internal and ghost nodes, and the
boundary machinery fills the ghosts.

Load balancing is handled by ``RedistributeNodes`` subclasses (space-filling
curves such as Peano-Hilbert and Morton order, ParMETIS, Voronoi, and
sort-and-divide), which the controller can invoke periodically.

On-node parallelism uses OpenMP (``src/Threading``) and, increasingly, RAJA
kernels with CHAI-managed views for GPUs (see ``SPH_RAJA`` and the
ArtificialViscosity implementations).

The Python Layer
================

Bindings
--------

Each directory ``src/PYB11/<Module>`` contains Python files that *describe*
the C++ interface using PYB11Generator decorators (``@PYB11virtual``,
``@PYB11template``, ...).  At build time PYB11Generator turns these
descriptions into pybind11 C++ code, which is compiled into one Python
extension module per Spheral module and linked against the C++ library.
Virtual methods are exposed with trampolines so that they can be overridden
in Python.

Convenience Layer
-----------------

On top of the raw bindings, Spheral provides:

- **Per-dimension namespaces** (``Spheral1d``, ``Spheral2d``, ``Spheral3d``,
  ``SpheralRZ``, ``SolidSpheral3d``, ...) that import everything with the
  dimension suffix stripped, so scripts can write ``SPH`` rather than
  ``SPH2d``.
- **Factory functions** that select the right class for the dimension and
  material type and assemble sub-packages, e.g. ``SPH(...)`` and ``ASPH(...)``
  in ``src/SPH/SPHHydros.py``, or ``makeFluidNodeList``.
- **SpheralController** (``src/SimulationControl/SpheralController.py``),
  which runs the outer loop: ``advance(goalTime)`` and ``step()``, periodic
  and rolling restart files (``dropRestartFile`` / ``loadRestartFile``),
  visualization dumps, periodic work callbacks, conservation monitoring,
  redistribution, and ``iterateIdealH`` for initializing smoothing scales.

A Typical Script
----------------

.. code-block:: python

   from Spheral2d import *

   WT    = TableKernel(WendlandC4Kernel(), 1000)
   eos   = GammaLawGasMKS(5.0/3.0, 1.0)
   nodes = makeFluidNodeList("gas", eos)          # NodeList
   # ... use a NodeGenerator to fill `nodes` ...

   db = DataBase()                                # registry of NodeLists
   db.appendNodeList(nodes)

   hydro = ASPH(dataBase = db, W = WT)            # physics package

   integrator = CheapSynchronousRK2Integrator(db)
   integrator.appendPhysicsPackage(hydro)

   control = SpheralController(integrator, kernel = WT,
                               restartBaseName = "myRun")
   control.advance(goalTime)

See ``tests/functional`` for many complete examples.

Writing a Physics Package in Python
===================================

Because ``Physics`` is exposed with overridable virtual methods, a new package
can be written entirely in Python by subclassing ``Physics`` and implementing
the required methods.  The following example, adapted from
``tests/functional/Damage/ExpandingTube/ExpandingTube-3d.py``, caps particle
speeds and deposits the removed kinetic energy into thermal energy at the end
of every step:

.. code-block:: python

   class VelocityDiffuser(Physics):

       def __init__(self, vmax):
           self.vmax2 = vmax*vmax
           self.vmax = vmax
           Physics.__init__(self)

       # Required interface -- this package evolves no state of its own.
       def registerState(self, dataBase, state):
           return
       def registerDerivatives(self, dataBase, derivs):
           return
       def evaluateDerivatives(self, time, dt, dataBase, state, derivs):
           return
       def dt(self, dataBase, state, derivs, time):
           return pair_double_string(1e30, "No vote")
       def label(self):
           return "VelocityDiffuser"

       # Do the work at the end of each step.
       def finalize(self, time, dt, dataBase, state, derivs):
           velocities = state.vectorFields(HydroFieldNames.velocity)
           energies   = state.scalarFields(HydroFieldNames.specificThermalEnergy)
           for vel, eps in zip(velocities, energies):
               for i in range(vel.numInternalElements):
                   vmag2 = vel[i].magnitude2()
                   if vmag2 > self.vmax2:
                       eps[i] += 0.5*(vmag2 - self.vmax2)
                       vel[i] *= self.vmax/sqrt(vmag2)

   integrator.appendPhysicsPackage(VelocityDiffuser(vmax = 1.0))

Points to keep in mind:

- Call ``Physics.__init__(self)`` in the constructor.
- ``state`` and ``derivs`` are accessed by key, using the names in
  ``HydroFieldNames`` (and similar classes) for standard fields.
- A package that evolves its own field should create it in ``registerState``
  and enroll it with an update policy (e.g. ``IncrementState``), register its
  derivative in ``registerDerivatives``, and fill the derivative in
  ``evaluateDerivatives``.
- Loop over ``numInternalElements`` unless you deliberately want to touch
  ghost nodes.
- Python packages run on the host only; Python overrides are not available
  in GPU kernels.

Build Structure
===============

Each ``src/<Module>/CMakeLists.txt`` contributes its sources, along with the
instantiation files generated from ``*Inst.cc.py``, to a single C++ library.
That library is built static, shared, or (for ``ENABLE_DEV_BUILD``) as an
interface over per-module shared libraries for faster rebuilds.  The PYB11
extension modules are then built and linked against it.  See
:ref:`CMake Configs` for the relevant options.
